# 组装器直接生成 demo，废除配方与接线引擎

组装器（coding agent）接收需求后直接写 demo 代码，代码是唯一真相源；配方、接线引擎、配方 schema 全部移除。生成时组装器在会话内产一份瞬态 spec（组件/参数/连线声明），薄校验器当场校验后即弃；对最终 demo 代码再做 AST 校验（参数名/枚举/范围比对组件注册表，值级分层）。消融改走运行时注入（统一协议 `set_param`/`replace_part`/`disable_part`），不再重建变体 demo。

未来读者会问"为什么砍掉接线引擎和配方"——答案：配方的确定性保证只对"出生那一刻"成立，而 ADR-0001 自己的"调试即编程"意味着 demo 一旦被改，配方就永远追不上实例；接线引擎的模板编码的正是最不稳定、最会被真实业务改掉的 agent loop。同时接线引擎是"9 分校验、1 分生成"，砍掉生成只省几十行，真正有价值的参数校验以独立薄校验器保留。

## Status

supersedes ADR-0001

## 背景决策链（issue #27 讨论结论）

1. **消融与接线器解耦**：消融从"配方重建变体"改为"运行时注入"——组件实现统一注入协议（`set_param`/`replace_part`/`disable_part`），消融 runner 机械调用，不读任何逐组件声明；"什么能注入"是组件使用说明文本，组装器 AI 读。
2. **接线引擎/配方/schema/TS-Python JSON 硬边界全部移除**（ADR-0003 相应修订）。组装器直接写 demo 代码，代码=唯一真相源。
3. **spec 是瞬态参考**：首次生成时的组件/参数/连线声明，生成时校验后即弃，不持久、不追代码。
4. **双层校验，同一权威源**：spec 校验（生成时，复用现有 validate）+ AST 代码校验（产物时，参数名/枚举/范围比对 registry）。两层都锚定组件注册表单一权威源；catalog 等任何手抄副本不得参与校验（漂移会造成"权威歧义"，纠错时多份来源互相矛盾）。
5. **组装器知识分层**：skill = 稳定知识（常驻上下文）；契约 diff = 变动知识（组件版本变化时才注入）；registry = 单一权威源（校验器直读）。契约文件是 registry 导出的只读视图，永不手改。
6. **代码自由、组件接触面显式**：编排逻辑自由，但组件使用必须是字面可识别的构造调用，AST 校验才能识别；参数值分三层——字面量全量校验、变量参数校验参数名、动态拼接仅确认是构造调用。
7. **可注入性 = 统一协议 + 文本说明**，无逐组件结构化声明。
8. **build-note 是纯信任文档**："为什么这么选"，可参考，不作为真相源。

## 连带后果（需实施工单）

- 消融运行时注入：组件基类/协议新增 `set_param`/`replace_part`/`disable_part`；agent 接受空零件（`_agent_parts` 强制三件套的约束重写）。
- 组装器服务化（原 #26）从"增强"升级为路线 B 前置依赖——浏览器无真实 coding agent，需服务端跑组装器产出 demo 代码。
- `assembler/src/catalog.ts` 从手抄改为由 registry 导出的只读契约；校验统一锚定该来源。
- 复用载体 = 导出的 demo 项目本身 + agent-design skill（create-llama 的 use case 预设模式），需沉淀第一个"已知良好示例"当锚点。
